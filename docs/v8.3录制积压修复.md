# v8.3 录制启动后立即积压停止

2026-10-18。用户提供 v8.2 实机日志：标定 RMS 0.12 px，录像启动后约一秒停止，报 `Disk cannot keep up`。仅从该信息无法判定保存盘本身的速度；用户日志中的 `D:\DataCollection` 安装不在当前开发机器上，本次未读取其 session 原始文件。

## 复现与原因

旧版视频与 IMU 共用 96 项队列，一个线程顺序完成三路 FFV1 编码与元数据写入。开发机器模拟三路 1280×720@30、两路各 300 Hz IMU，不给生产者额外节流，约 0.14 秒后队列达到 96，已接收 99 个样本；排空后每路仅五帧，整段标为不完整。报告为 `software/logs/recording_baseline_v8_2.json`。

高熵测试图像下，旧 RGB FFV1 编码明显低于输入帧率，灰度 FFV1 同样不足；因此先解决编码与排队结构，不能直接把提示归因为用户硬盘损坏。编码探测记录在 `codec_throughput_probe.json` 与 `raw_codec_throughput_probe.json`。

## 修改

- 每路视频各一队列和写入线程，IMU/已编码帧索引独立写入。默认视频缓存按图像字节限制为 256 MB，元数据队列不携带图像，防止一帧耗时阻塞高频 IMU。
- 默认快速无损保存 IR 原始 Y800 与 RGB 原始 RGBA，保持完整像素；提供 FFV1 模式供有足够 CPU 吞吐的机器选择。配置与输出文件记录实际模式。像素格式选择依据 [OpenCV 5.0 FFmpeg 后端](https://raw.githubusercontent.com/opencv/opencv/5.0.0/modules/videoio/src/cap_ffmpeg_impl.hpp)，并以实测回读校验为准。
- 部分编码即使被称为无损，在 OpenCV 输入像素转换后也可能不保留原值。本机探测发现 FFVH 彩色和 HFYU 灰度回读不完全一致，因此未用于默认模式。
- 1280×720@30 三路原始写入约 166 MB/s、10 GB/分钟，界面展示空间占用。用户可以直接测试所选保存目录；三秒短测覆盖编码和写入排队，并强制刷新操作系统写缓存，不代表所有长期负载都已验证。
- 每段保存逐路队列峰值、写入耗时、样本计数和错误类别。拒绝样本会被明确记录；仍不能把不完整段当成成功。原始无损数据、帧索引、位姿戳、音轨和 IMU 保留。
- 低于 512 MB 可用空间停止并排空数据。低空间检查不持有 SDK 回调锁。停止时先排空视频线程，再结束索引线程，最后核对实际帧数与已接收/已写计数。

## 验证

新流程的三秒测试：三路各 90 帧，共 270 帧，同时 1,800 条 IMU，计数完整、首尾帧像素一致，无持续缓存增长。另做 45 秒长段：三路各 1,350 帧，共 4,050 帧，生成约 7.47 GB 视频，RGB 单文件超过 4 GB；首尾帧可寻址回读，计数完整，无持续积压。报告为 `recording_throughput_v8_3.json` 与 `recording_large_avi_v8_3.json`。

`check_recording_throughput_v8_3.py` 覆盖编码器被阻塞时仍能独立写完 2,000 条 IMU、16 MB 视频缓存上限、停止后排空已接收帧、三路 720p/30 FPS 加高频 IMU 的实际节奏测试、原始像素抽查，以及界面后台测速和临时文件清理。此前的编码静默丢帧检查继续执行。

本次使用开发机器上的合成数据；未连接真实 D435i，也未在用户 D 盘复测。保留真实采集目录测速与逐段性能统计，以便进一步分辨目标机器的编码、存储或持续负载问题。当前在线包为 `releases/D435I_ThreeHost_v8_3.zip`，本机标定 JSON 可继续加载。

完整回归通过 10/10，包括采集、引导标定、结算、本机标定后录制、统一启动、旧版处理、重建融合、编码静默丢帧和新录制吞吐检查。另验证了编码完成后才到达的较早 IMU 运动事件，最终帧位姿有效性会按事件时间统一校正。
