# v8.4 录像压缩与播放

v8.3 为降低编码负载而默认采用 RGB RGBA、IR Y800 原始 AVI，1280×720@30 三路约 165.9 MB/s，12 秒约 1.99 GB。该体积来自未压缩像素；RGBA/Y800 也存在通用播放器支持差异。此前仅通过 OpenCV 回读，不能代表 Windows 普通播放器可播放。

## 当前保存方式

| 模式 | RGB | IR1 / IR2 | 用途 |
| --- | --- | --- | --- |
| 默认 balanced | H.264 CRF18、yuv420p、MP4 | FFV1 level3、gray、AVI，像素无损 | 降低存储，保留红外测量像素 |
| mp4 | H.264 CRF18 MP4 | H.264 CRF12 MP4，有损 | 通用播放及更小体积，测量精度另验 |
| fast_lossless | 原始 RGBA AVI | 原始 Y800 AVI | 原始无压缩，体积很大 |
| ffv1 | 旧 OpenCV FFV1 AVI | 旧 OpenCV FFV1 AVI | 旧全无损模式，CPU 开销较高 |

压缩模式通过固定版本 imageio-ffmpeg==0.6.0 的 Windows FFmpeg 执行程序编码，启动器自动安装，无需配置系统 PATH。FFmpeg 进程隐藏运行。每路独立线程/队列，IR FFV1 使用 slice 并行编码；保留内存上限、独立 IMU、低磁盘空间处理和故障不完整标记。每帧仍保存原始设备时间与 pose_stamp_id。

session.json 保存实际编码及 lossy_streams，frames.jsonl 保存文件名、video_index 和 pixel_lossless。重建与合成按实际文件名读入，并在 sources 中保留 MP4 原始文件。输出视频为配置的恒定帧率；遇到采集帧号缺口时，真实时序仍以 frames.jsonl 为准。

## 保存状态与历史录像

结束录像先排空编码、关闭编码器并检查退出码，再核对视频帧数和抽样解码首、中、尾帧。summary.json 新增逐文件大小、时长、编码、检查范围和验证耗时；界面日志显示逐文件摘要。速度测试把抽样解码耗时与排空/磁盘刷新耗时分别报告，解码检查本身不计为写盘瓶颈。

工作台“录像检查／转 MP4”使用独立后台进程。检查报告区分采集不完整、帧号缺口、索引重复/缺失、视频缺失和不可解码；可执行逐帧完整解码。导出写到新的 mp4_playback 子目录，保留原始文件不覆盖，使用 H.264/yuv420p/faststart 并逐帧验证输出。现有 H.264 MP4 直接复制视频码流。音轨保留在原 session WAV。转换不修复此前未采集到的帧，也不把原始不完整状态变为完整。

## 验证范围

自动检查涵盖 IR 全灰度随机像素逐帧一致、MP4 在 Windows Media Foundation 解码、旧 RGBA/Y800 导出及原文件摘要不变、坏帧索引拒绝、编码器结束失败标记、全分辨率三路 30 FPS 与高频 IMU 压力测试、后台检查/导出界面以及本机重建和三机融合保留 MP4。

2026-10-18：原有 10 项检查通过；新增 check_video_storage_v8_4 在修复新窗口的中文路径 Qt 插件初始化后通过。新增压力测试为 6 秒、每路 180 帧（1280×720@30）及高频 IMU；完整统计保存于 software/logs/video_storage_v8_4.json。Windows Media Foundation 在独立进程中确认 H.264 MP4 可解码且彩色通道正确。专用环境启动脚本的 SetupOnly 和完整环境诊断通过。

这些测试使用合成图像，不能代替实际相机画面的压缩率、真实硬盘长期吞吐或面部测量精度验证。默认 RGB 是有损数据，红外无损；选择三路 MP4 会改变测量像素。用户反馈的外部 D 盘录像尚未取得，本次不能据此判断其原文件是否损坏。
